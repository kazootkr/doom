# create-requirement

ユーザーのプロンプトの要望を、spec 駆動開発の起点となる要求ファイル（`docs/requirements/` 下の org 形式）に落とし込む。成果物は要求ファイル1つのみ。CLAUDE.md の開発スタイルに従い、 **タスク（docs/tasks/）の作成や実装コードの変更はこのスキルで行わない**（タスク化はユーザーが 別途指示したときだけ）。

## モード判定

引数の先頭が `req-<番号>`（例: `req-3`）形式かで挙動が分かれる。この形式に一致するときだけ既存要求の指定とみなす（`3` 単体やファイル名は受け付けない）。

```sh
ls docs/requirements/req-<N>_*.org 2>/dev/null
```

- **指定があり対応ファイルが存在する → 追記モード**: そのファイルに要求を追記する。新規ファイルは作らない（要求番号を新たに採番しない）。要求 → タスク化 → 実装 → ユーザー動作確認の後に出た課題・変更依頼・不具合を、同じ要求番号を引数に渡して反映する用途（例: `create-requirement req-3 不具合があったので修正検討してください…`）。
- **指定がない（純粋に新しい要望だけ）→ 新規作成モード**

## 手順（共通）

1. **事実関係の調査**: 背景に書く内容（現状の設定・挙動、根本原因、関連する既存の要求/タスク）はリポジトリを調査して裏付ける。プロンプトにない要求を推測で膨らませない — 要求一覧に載せるのはユーザーが求めたことだけで、調査で得た事実は背景・制約に書く（推測は「〜と思われる」と区別するか書かない）。提案（みやすい設定等）を検討する際は、相当する doom モジュールが既にないかも確認する（doom-first・CLAUDE.md 実装方針）。

2. **本文の作成**: モードに応じて「新規作成モード」または「追記モード」を実行する。

3. **報告**: 対象ファイルへのリンクと要求の要約（追記モードでは今回追加した R 番号とその要点）を伝える。タスク化はユーザーの指示を待つ。

## 新規作成モード

1. **採番**: 既存ファイルの最大番号 + 1。要求ファイルの削除で欠番が生じていても、その番号は再利用せず常に最大番号 + 1 とする。

   ```sh
   ls docs/requirements | sed -n 's/^req-\([0-9][0-9]*\)_.*\.org$/\1/p' | sort -n | tail -1
   ```

2. **subject 決定**: 要求の主題を表す短いケバブケース英語（例: `ns-inline-patch`, `ime-focus-guard`）。日本語・スペースは使わない。

3. **ファイル作成**: `docs/requirements/req-<番号>_<subject>.org` に下記テンプレートで書く。

## 追記モード

1. 対象 `docs/requirements/req-<N>_*.org` を読み、subject・既存の要求番号（req-<N>.1, req-<N>.2…）・非機能要求/受け入れ確認手順の構成を把握する。

2. **要求一覧への追記**: `* 要求一覧` の末尾に、最大ローカル番号 + 1 の新セクション（`** req-<N>.<次番号>: …`）を追加する。課題・不具合が既存要求のどれに起因するか分かる場合は本文で参照する（例: 「req-<N>.2 の〜が原因と考えられる」）。

3. **背景・受け入れ確認手順の補足**: 必要なら背景に経緯（動作確認で見つかった課題等）を、受け入れ確認手順に対応する確認項目を足す。

4. **既存記述を壊さない**: 既存の要求・背景・制約は作り直さず追加分だけ足す。要求番号の意味は変えない（振り直さない・欠番が出ても詰めない）。項目の削除（取り消し）で生じた欠番は新しい要求項目に再利用せず、常に最大ローカル番号 + 1 で採番する。

## テンプレート

`#+title` はファイル名から拡張子を除いたものと一致させる。

```org
#+title: req-<番号>_<subject>
#+STARTUP: indent
#+STARTUP: showall
#+STARTUP: nolineimages
#+STARTUP: hidestars

* 背景

<なぜこの要求が生まれたか。経緯・現状の課題・根本原因・前提となる環境情報。
関連する既存の要求/タスクがあれば org リンクで参照する:
[[file:req-N_xxx.org][req-N xxx]] / [[file:../tasks/task-N_xxx.org][task-N]]>

* 要求一覧

** req-<番号>.1: <要求のタイトル>（必須）

<要求を「〜すること」の宣言文で書く。続けて箇条書きで実現手段・条件を具体化し、
必要なら理由（なぜそれが必要か）を補足する>

** req-<番号>.2: <要求のタイトル>

<以下同様。優先度が高いものに（必須）を付ける>

* タスクへの引き継ぎ（任意）

<ユーザーが指定した確定コードや、後続タスクへ渡したい参照スニペットがあるときだけ置く。
無ければこのセクションごと省略する。実装手段の設計はタスク側で行う>

* 非機能要求・制約

- <設定・コードの配置先>
- <ガード条件: 対象外環境（パッチ未適用・Linux 等）で no-op になること>
- <検証環境の制約: docker で検証できない範囲と、その最終確認の方法>

受け入れ確認手順:

- [ ] <ユーザー観点で検証可能な確認項目>
- [ ] <既存動作が退行しないことの確認項目>
```

## 内容の書き方

- 要求項目は `req-<N>.<n>`（N=この要求ファイルの番号、n=ファイル内の連番、`req-<N>.1` から）で採番する。
  config.el のコメント等にも書かれるため、どの要求の項目か一意に判別できるようにする。
- 要求は実装手順書ではなく「満たすべき状態」を書く。実装手段（関数の組み方・hook/advice の配線・
  recipe 文字列等）はタスクへ委ね、要求本文にコードを書かない。例外として、ユーザー指定の確定コードや
  後続タスクへ渡す参照スニペットは、本文に混ぜず `* タスクへの引き継ぎ` セクションに分離して載せる。
- Emacs のシンボルやコードは org の verbatim（=symbol=）で囲む。
- 受け入れ確認手順はチェックボックス（`- [ ]`）にし、後続タスクの完了条件にそのまま流用できる
  粒度で書く。

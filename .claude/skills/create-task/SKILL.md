# create-task

引数で指定された要求ファイルを、spec 駆動開発の実装ステップの起点となるタスクファイル（`docs/tasks/` 下の org 形式）に落とし込む。成果物はタスクファイル1つのみ。CLAUDE.md の開発スタイルに従い、タスク化はユーザーの明示的な指示があったときだけ行い、**実装コードの変更はこのスキルで行わない**（実装は別途指示があったとき完了条件に沿って進める）。

**要求ファイルとタスクファイルは必ず 1 対 1 で対応する。** タスクの番号・subject は対応する要求と常に一致させ（例: `req-2_org-notes` ↔ `task-2_org-notes`）、独立採番（最大番号 + 1）はしない。`req-N` を起点に複数タスクを作らず、同じ要求への追加・変更は対応する既存タスク1つを更新して取り込む。要求側で削除されて欠番になった番号は、新しいタスクに再利用しない（採番は要求に追従する）。

## 手順

1. **要求ファイルの解決**: 引数は `req-<番号>`（例: `req-1`）形式で受け取る（`1` 単体やファイル名は受け付けない）。`docs/requirements/req-<番号>_*.org` を特定して読み、要求の **番号 N** と**subject** を確定する。見つからなければ `docs/requirements/` の一覧を提示して確認する。

2. **対応タスクの特定**: タスクのファイル名は要求と 1 対 1 で `docs/tasks/task-<N>_<subject>.org`（番号・subject とも要求と同一）。この名前のファイルの有無で挙動を分岐する。

   ```sh
   ls docs/tasks/task-<N>_*.org 2>/dev/null
   ```

   - **存在しない → 新規作成モード**（手順 3〜4 → 5a）
   - **存在する → 更新モード**（手順 3〜4 → 5b）

3. **実装対象の調査**: 要求の「非機能要求・制約」が示す配置先（config.el 等）の現状をリポジトリで確認し、「やること」を具体的な変更内容として書けるようにする。既存ブロックへの追記なら該当箇所（ファイル名:行番号）を特定しておく。実装方法を検討する際は、相当する doom モジュールが既にないかも確認し、あればモジュール有効化を優先検討する（doom-first・CLAUDE.md 実装方針）。

4. **要求との差分把握**: 更新モードでは既存タスクを読み、要求側で追加・変更された内容（新しい R 番号、受け入れ確認手順の増分など）を洗い出す。

5a. **新規作成**: `docs/tasks/task-<N>_<subject>.org` に下記テンプレートで書く。

5b. **既存タスクの更新**: 既存ファイルを編集し、要求の差分を「やること」と「完了条件」に取り込む:
   - 検証済みで `[X]` の完了条件は、実態が変わらない限り `[X]` のまま残す
   - 要求に増えた分は「やること」に =** TODO [#優先度]= の見出しで追記し、対応する完了条件を `[ ]` で追加する。見出し先頭の要求番号（req-<N>.<n>）は要求側に一致させ、削除で生じた欠番は再利用しない（要求の採番に追従する）。要求側で取り消された項目は、見出しと対応する完了条件をタスクから削除する（要求↔タスクは 1:1 なので要求に無い項目はタスクにも残さない。これは要求差分の反映であってスコープ外の改変ではない）
   - 新規項目で親項目が「全て完了」と言えなくなったら、その親の `[X]` を `[ ]` に戻す（チェックは実態の記録）
   - 既に達成済みの項目を作り直さない・消さない（スコープ外の改変をしない）
   - **動作確認後に判明した不具合の修正は要求ファイルに反映せず、このタスクに反映してから実装する。** 修正用の見出しを `** TODO [#優先度]` で追記し、要求番号に紐づかない修正は `fix-<n>` ラベルで起こす。根本原因と修正方針は背景に記録し、対応する完了条件を `[ ]` で足す（挙動が変わる確認項目は既存の `[X]` を `[ ]` に戻す）

6. **報告**: 対象ファイルへのリンクと、やること・完了条件の要約（更新モードでは今回の差分）を
   伝える。実装はユーザーの指示を待つ。

## テンプレート

`#+title` はファイル名から拡張子を除いたものと一致させる。

```org
#+title: task-<番号>_<subject>
#+STARTUP: indent
#+STARTUP: showall
#+STARTUP: nolineimages
#+STARTUP: hidestars

* どの要求に基づくタスクか

- [[file:../requirements/req-<番号>_<subject>.org][req-<番号> <subject>]]

* 背景

<要求の背景を要約: 課題が見つかった経緯、根本原因、採用する解決方針。
関連する既存タスクがあれば org リンクで参照する:
[[file:task-N_xxx.org][task-N]]>

* やること

<実装対象（配置先ファイルと該当箇所）を冒頭の本文で示す。
個々の変更内容は org の見出し（=**=）で1項目=1見出しにし、進捗キーワードと優先度で管理する:
  =** TODO [#A] req-<N>.1 <変更内容>=
- 進捗: 未着手は =TODO=、=/sync-implementation= で実装・検証が済んだら =DONE=。
- 優先度: =[#A]= / =[#B]= / =[#C]= で実装の重要度・着手順を表す。
- 各見出しは原則1つの要求番号と 1 対 1 で対応させ、その要求番号（req-<N>.1）を見出し先頭に置いてトレーサビリティを保つ。1 見出しが例外的に複数要求にまたがる場合は、主たる要求番号を先頭に 1 つだけ置き、残りは「完了条件」の各項目に番号を併記する。
- 見出し本文に具体的な変更内容・配置位置・=#+begin_src emacs-lisp= の実装スニペットを書く。>

* 完了条件

- [ ] <自動検証できる項目: config.el の構文チェック（batch モードの =check-parens=）等>
- [ ] <docker 環境（Linux）で確認できる項目: ガードによる no-op、エラーが出ない等>
- [ ] macOS の GUI Emacs を再起動し、以下をユーザーが確認する
  - [ ] <要求の受け入れ確認手順から転記した確認項目>
  - [ ] <既存動作が退行しないことの確認項目>
```

## 内容の書き方

- 背景は要求の丸写しではなく、「なぜこの変更をするのか」をすぐ掴める分量に要約する。詳細は冒頭の要求リンクに任せる。
- 「やること」は実装手順として具体的に書く。タスクが実装仕様の単一の正なので、要求の`* タスクへの引き継ぎ`（あれば）の確定コードを取り込み、残りは調査結果に基づいて設計する（HOW はタスクが持つ）。
- 「やること」の各項目は org の見出し（=**=）で1項目ずつ立て、進捗（=TODO= / =DONE=）と優先度（=[#A]= / =[#B]= / =[#C]=）を見出しに付けて管理する。`/sync-implementation` での実装・検証に応じて進捗キーワードを更新できるよう、最初は =TODO= で起こす。
- 冪等性: `/sync-implementation` を何度実行しても同じ最終状態に収束するよう、変更対象（ファイルと挿入位置・対象ブロック）を一意に特定し、「既にあれば変更しない」粒度で書く。自然に冪等でないelisp（=advice-add= 等）は一度だけ適用されるようアンカー編集／ガードする旨を明記する（=add-hook= / =add-to-list= / =setq= は冪等）。
- 決定性・再現性: 同じ環境で再実行すれば同じ実装に再現できるよう、タスクは自己完結させ外部の暗黙文脈に依存しない。実行時にしか確定できない分岐は実装者の裁量に委ねず、判断ルール（条件 → 結果）を明示する。
- 完了条件は要求の「受け入れ確認手順」を取り込みつつ、「自動検証できるもの」と「ユーザーによる手動確認（macOS 固有の動作等）」を分け、実装後にチェックを付けられる粒度で書く。1 見出しが複数要求にまたがる場合は、対応する完了条件の各項目に要求番号（req-<N>.<n>）を併記して、見出し先頭に載らない番号のトレーサビリティを補う。
- Emacs のシンボルやコードは org の verbatim（=symbol=）で囲む。

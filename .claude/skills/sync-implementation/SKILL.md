# sync-implementation

引数で指定されたタスクファイルの内容に実装を同期する。「同期」とは、やることをすべて実装し、完了条件を検証してチェックを付け、実装とタスク記述のずれを残さないこと。実装するのはタスクの「やること」に書かれた内容だけで、スコープ外の改善は実装せず報告にとどめる（必要なら要求化・タスク化を提案する）。

## 手順

1. **タスクファイルの解決**: 引数は `task-<番号>`（例: `task-2`）形式で受け取る（`2` 単体やファイル名は受け付けない）。`docs/tasks/task-<番号>_*.org` を特定して読む。見つからなければ`docs/tasks/` の一覧を提示して確認する。

2. **要求の参照**: 「どの要求に基づくタスクか」のリンク先要求ファイルを読み、要求番号（req-<N>.<n>）と受け入れ確認手順を把握する。やることの解釈に迷ったら要求側の記述を正とする。

3. **現状との差分確認**: 実装対象（config.el 等）の現状を読み、やることのうち未実装の項目を特定する。部分適用済みのタスクは未実装分だけ実装する（適用済みの項目を作り直さない）。

4. **実装**: やることを上から順に実装する。コメントには対応する要求番号（req-<N>.<n>）と要求ファイルへの参照を残し、タスクが指定する実現手段（=after!= の使用等）に従う。

5. **検証**: 完了条件のうち自動検証できる項目を docker 環境で実行する（CLAUDE.md の Docker 検証ルールに従う。特に: ホストで GUI Emacs を起動しない、batch の出力は =message= でなく =princ=、検証用の一時スクリプトは docker/out/ に置き終わったら削除する）。

   - 構文チェック: コンテナ内 Emacs で config.el に =check-parens=
   - 値や挙動の確認: =./docker/run.sh batch '<ELISP>'= で doom ロード後の状態を検証
   - macOS 固有・GUI 固有の項目はコンテナで検証できない。スキップしてユーザー確認に回す

6. **進捗・チェックボックス更新**: 実装し検証も通った「やること」の見出しは進捗キーワードを =TODO= → =DONE= にする。あわせて、検証が通った完了条件だけを =[X]= にする。未検証・ユーザー確認待ちの項目は見出しを =TODO= のまま・完了条件を =[ ]= のまま残す — 進捗キーワードもチェックボックスも実態の記録であり、実装した＝完了ではない（macOS 実機確認待ちなど検証が完了していない見出しは =DONE= にしない）。

7. **報告**: 実装内容（ファイルと該当箇所）、検証結果、完了条件から転記した残りのユーザー確認項目を伝える。macOS 実機での確認が必要な場合はその手順を具体的に示す。

## 検証で失敗したとき

- 検証が失敗したら、チェックを付けずに原因を調査して実装を直し、再検証する
- タスクの記述自体が誤っていた（実現手段が動かない等）場合は、勝手にタスクを書き換えて進めず、
  調査結果と修正案をユーザーに報告して判断を仰ぐ
- docker デーモン（colima）停止時はユーザーに =start-colima= の実行を依頼する

## 例

```
/sync-implementation task-2
```

1. docs/tasks/task-2_ime-focus-guard.org を読む → req-2 の req-2.1〜req-2.4 を把握
2. config.el を読み、req-2.1〜req-2.3 は適用済み・req-2.4 が未実装と判定
3. req-2.4 の =(after! diff-hl (setq diff-hl-update-async nil))= を実装
4. docker で check-parens と =diff-hl-update-async= の値を検証 → 通過
5. req-2.4 の見出しを =DONE= にし、該当する完了条件を =[X]= に更新し、macOS 実機の確認項目を報告
